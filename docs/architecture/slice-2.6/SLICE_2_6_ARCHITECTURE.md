### Component responsibilities and boundaries

| Component                                                                      | Owns                                                                                                                                                                            | Never does                                                             |
| ------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------- |
| `apps/api` · **repositories** module (new)                                     | Repo init from template, working tree, file reads/writes through a path-safe FS layer, page ↔ route-file sync, checkpoints (commits), history, restore, backup bundles          | Execute project code; mount the repo into a sandbox                    |
| `packages/code-index` (new library)                                            | Parse TSX (Babel), compute stable element ids, build the oid → source-range index; Vite plugin that injects the same ids into preview builds                                    | Network or FS access of its own; persisting ids into source            |
| `packages/project-template` (new)                                              | The versioned React app template and its lockfile; the allow-listed dependency set                                                                                              | —                                                                      |
| `packages/preview-protocol` (new)                                              | Zod schemas and versioning for every studio ↔ preview message                                                                                                                   | —                                                                      |
| `apps/api` · **preview-sessions** module (new)                                 | Session records, quotas, start/attach/stop, health reconciliation, file pushes to the agent                                                                                     | Proxy preview traffic (keeps studio cookies away from preview content) |
| `services/preview-gateway` (new deployable)                                    | Routing browser traffic for preview origins to the right sandbox; the control channel API → agent; sandbox provider calls (compose pool locally, ACA dynamic sessions in Azure) | Store project data; reach PostgreSQL, Redis, AI runtime or Key Vault   |
| `services/preview-agent` (new image, runs inside each sandbox)                 | Accept a workspace snapshot and file patches, run Vite, report status and build errors, serve the inspector script                                                              | Initiate any outbound connection                                       |
| `apps/web` · canvas (2.6: live frame and selection read-out; 2.7: full canvas) | Iframe, protocol client, overlays, viewport controls                                                                                                                            | Trust any message whose origin, source or schema doesn't match         |

Why a separate gateway rather than proxying through the API: the API carries the studio session cookie and CSRF state. Untrusted preview content must be served from a different site, and the component serving it should hold nothing worth stealing. The gateway is the single new long-running service besides the sandbox image, which keeps to the "no unnecessary microservices" rule.

## 3. End-to-end journey (acceptance path)

```
Create project ─► API creates DB rows and initialises the repo from template v1, first commit "Create project"
Create page    ─► API writes src/pages/<name>/<Name>Page.tsx, regenerates src/app/routes.ts, updates DB projection
Start preview  ─► POST /projects/:id/preview-sessions → gateway allocates sandbox → API pushes working-tree snapshot
                   → agent starts Vite with the oid plugin → status "ready"
Display        ─► Canvas iframe loads https://s-<cap>.preview…/ ; inspector handshakes with the studio
Select element ─► inspector reports {oid, rect}; studio asks API GET /projects/:id/code-index/:oid
Identify source─► API returns {file, line, column, range, component} from the oid index of the current revision
Edit source    ─► (2.7) POST /projects/:id/edits {baseRevision, ops} → AST edit → file pushed → Vite HMR
Checkpoint     ─► POST /projects/:id/checkpoints → git commit on main, recorded in project_checkpoints
```

2.6 delivers everything up to **identify source** plus the checkpoint API. Structured edits (the "edit source" step), undo/redo and the full canvas UI are slice 2.7. This keeps 2.6 to infrastructure and safety work.

## 4. Changes to the earlier Phase 2 plan

| Earlier plan                                                               | Problem found                                                                                                                                                                                                                                                                        | New decision                                                                                                                                                                                                                                                                                                                     |
| -------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| One preview-runtime container hosting many Vite servers                    | One project's code could read another project's files or processes in the same container                                                                                                                                                                                             | One sandbox per preview session (local: pool of single-session containers; Azure: one ACA dynamic session each)                                                                                                                                                                                                                  |
| Iframe `sandbox` **without** `allow-same-origin` and penpal origin pinning | The framed document gets an opaque origin `"null"`, so the studio can't post to it without `targetOrigin '*'` and can't validate `event.origin` — this contradicts the "no wildcard postMessage" requirement. Vite's module scripts would also need `Access-Control-Allow-Origin: *` | `sandbox="allow-scripts allow-same-origin allow-forms allow-modals"` **on a separate registrable domain** with a per-session host. Isolation comes from the cross-site origin; exact origin checks become possible. `allow-same-origin` is only dangerous when the frame is same-origin with the parent, which can't happen here |
| HMAC shared secret between API and preview runtime                         | A second secret type to manage                                                                                                                                                                                                                                                       | Same IdP JWT pattern as ADR-0011 for API → gateway; per-session random agent tokens inside the gateway → agent hop                                                                                                                                                                                                               |
| Pages "derived from a route manifest" with the DB as cache                 | Agreed                                                                                                                                                                                                                                                                               | Kept; `core.project.json` is the manifest and `project_pages` is its projection                                                                                                                                                                                                                                                  |
| Repo storage on a volume, git via isomorphic-git                           | isomorphic-git lacks worktrees (needed for agents) and bundle/fsck                                                                                                                                                                                                                   | Hardened git CLI in the API image (decision D9), same volume plan                                                                                                                                                                                                                                                                |

## 5. Answers to the architectural questions

**1. Separate repository or managed worktree?** Both, at different levels. Every project gets its **own git repository** — a separate directory and object store, so it's the unit of isolation, backup, export (Azure Repos sync) and deletion, with no shared object database between projects or teams. Inside that repository the API keeps **one shared working tree** on `main` that the canvas edits. **Managed git worktrees** are added later for AI agents (`agent/<run>` branches) so long-running agent work never edits the user's tree directly.

**2. Separate container per preview or another boundary?** A separate sandbox per preview session. In Azure, **Azure Container Apps dynamic sessions (custom container)**: each session is a Hyper-V-isolated sandbox with its own kernel, egress can be disabled, no managed identity is assigned, and idle sessions are reclaimed. That is a stronger boundary than a container on a shared kernel, and it fits the existing Container Apps target with no new platform. Fallback if the validation spike fails (WebSocket/HMR through the pool endpoint, or start time): one Azure Container Instances container group per session in an egress-denied subnet. Rejected: shared multi-project containers (weak isolation), AKS with gVisor/Kata (new platform to run), WebContainers/CodeSandbox (commercial licences and third-party execution). Locally: a pool of single-use containers on an internal-only Docker network, recycled after every session, with no Docker socket anywhere.

**3. Multiple preview sessions for one project?** One active preview session per project (per working tree), shared by every viewer on that team: the API reference-counts viewers through heartbeats and stops the sandbox after the last one leaves plus an idle timeout. Everyone sees the same working-tree state, which matches the single shared tree. Per-user sessions are only needed once there are per-user branches (agents, Phase 4); the session record is keyed by `(project, ref)` so that extension needs no redesign. Quotas cap sessions per team and globally.

**4. Mapping a DOM element to exact React source?** At transform time the Vite plugin (`@core-studio/vite-plugin-oid`) adds `data-core-oid="<id>"` to every JSX element it compiles. The id is a deterministic hash of the file path and the element's structural path, computed by `packages/code-index`. The API runs the **same function** over the same file revision to build an index `oid → {file, start/end line/column, element name, component name}`. Because both sides compute ids from the same source revision, no id is ever written into the customer's source. Component instances also get `data-core-instance` so selection can resolve either the instance (call site) or the definition. Full details and edge cases (fragments, lists, conditional renders, components that don't forward props) are in [PREVIEW_COMMUNICATION_PROTOCOL.md](PREVIEW_COMMUNICATION_PROTOCOL.md) §5.

**5. Installing third-party dependencies safely?** In 2.6 there are **no installs at all**. The preview image carries a fixed, allow-listed `node_modules` built in CI from the template lockfile (scanned by Trivy and `pnpm audit`, install scripts off), mounted read-only. A project's `package.json` may only reference allow-listed packages at the pinned versions; anything else fails validation before it reaches the sandbox. Later: an add-dependency request runs in a separate builder sandbox whose only egress is an internal registry proxy (Azure Artifacts upstream feed) with `--ignore-scripts`, a licence and vulnerability policy, and a lockfile-hash-keyed read-only layer cache in Blob Storage. The preview sandbox itself never gets network access to install anything.

**6. Persisting preview state and recovering after restarts?** Previews hold no state worth keeping: the working tree on the repo volume and the session row in PostgreSQL are authoritative. A reconciler in the API compares session rows with the gateway's view every 30 s and on start-up, marks lost sandboxes `error: sandbox_lost`, and the studio offers "Restart preview", which allocates a fresh sandbox and re-pushes the snapshot at the current revision. Unsaved canvas edits are never lost because each edit is written to the working tree before it is pushed to the preview.

**7. Preventing previews from reaching internal infrastructure?** Layered: (a) no route — Azure sessions with egress disabled, a local Docker network with `internal: true` whose only other member is the gateway, which doesn't listen on that network; (b) nothing to steal — no environment secrets, no managed identity, no cloud metadata endpoint reachable from a Hyper-V session, no repo volume mount; (c) the browser side — a separate registrable domain, so preview JavaScript can't read studio cookies or call the studio API with the user's session (CORS plus the API's Origin check); (d) verification — container tests that try to reach the API, PostgreSQL, Redis, the AI runtime, the gateway control port, `169.254.169.254` and the internet, and expect every attempt to fail.

**8. Future AI agents editing the same files safely?** Every writer goes through the same API edit pipeline — canvas operations, the code editor and agents alike. Agents never touch the filesystem. The pipeline takes a per-project lock (PostgreSQL advisory lock), checks `baseRevision`, validates paths (repo-relative, no `.git`, no symlinks), re-parses the result and bumps the revision. Interactive edits apply directly to the shared tree. An agent run works in its own worktree on `agent/<run-id>` from a known commit and proposes a change set; merging back is a 3-way merge through the same pipeline, and conflicts go to the user. Checkpoints before and after each agent run make every agent change revertible as a normal new commit.

## 6. Key trade-offs

| Choice                                     | Benefit                                                             | Cost                                                             | Mitigation                                                                                                |
| ------------------------------------------ | ------------------------------------------------------------------- | ---------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| Derived oids (not written into source)     | Customer code stays clean; no stale or duplicated ids from AI edits | Ids shift when siblings are inserted                             | The API returns an `oidRemap` after every edit; selection follows it                                      |
| One shared working tree per project        | Simple, everyone sees the same thing, one preview                   | No parallel branches for humans                                  | Worktrees for agents; per-user branches are possible later because sessions are keyed by `(project, ref)` |
| Hardened git CLI instead of isomorphic-git | Worktrees, bundles, fsck, gc, performance                           | Adds a binary to the API image (CVE surface)                     | Fixed arguments, no shell, hooks disabled, system config ignored, Trivy gate                              |
| ACA dynamic sessions                       | Hyper-V isolation, scale to zero, no new platform                   | Newer service; WebSocket and start-time behaviour must be proven | Spike S1 before any Azure commitment; ACI fallback behind the same provider interface                     |
| Allow-list-only dependencies in 2.6        | Smallest supply-chain surface                                       | Generated apps can only use the template's packages              | The controlled install pipeline is a planned follow-up, not a redesign                                    |
| Separate preview domain                    | Strong browser isolation and exact origin checks                    | Needs a second domain and wildcard TLS certificate               | Decision D12; locally `127.0.0.1` vs `localhost` are different sites                                      |

## 7. Risks

| ID  | Risk                                                                                                 | Likelihood / impact | Response                                                                                                                                |
| --- | ---------------------------------------------------------------------------------------------------- | ------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| A1  | ACA dynamic sessions can't carry Vite's HMR WebSocket through the pool endpoint, or start too slowly | Medium / high       | Spike S1; ACI fallback; worst case HMR degrades to full reloads (functionally acceptable)                                               |
| A2  | git on Azure Files (SMB) has locking and permission quirks                                           | Medium / high       | Spike S2: prefer NFS shares; single-writer per project via advisory locks; nightly `git fsck`                                           |
| A3  | Derived oids diverge between the API index and the preview build                                     | Low / high          | One shared package, identical Babel parser options, revision tagged on every message, property tests                                    |
| A4  | Vite or inspector bugs break the preview for valid code                                              | Medium / medium     | Build and runtime errors are reported as typed messages; preview failure never blocks editing or checkpoints                            |
| A5  | Cost growth from many concurrent previews                                                            | Medium / medium     | Per-team quotas, idle stop after 10 minutes, small ready pool, usage metrics in slice 2.10                                              |
| A6  | The team cannot run Azure spikes (no deploy rights)                                                  | High / high         | Local implementation proceeds; the Azure provider ships behind a config switch and is enabled only after someone with access runs S1/S2 |
| A7  | The preview domain or certificate is not approved                                                    | Medium / medium     | Local development is unaffected; production stays at `FEATURE_CANVAS=internal`                                                          |
